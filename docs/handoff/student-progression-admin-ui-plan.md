# Student progression — admin UI implementation plan

**Status:** plan reviewed; all five open questions decided (§d). No feature code written yet.
Ready to become an M0/M1 build brief.
**Backend:** merged to `staging` (#268, #270, #272, #273, #274, #275). Config tables, both
migration jobs, the reassignment service, three commands and the `promoted_requires_link` trigger
all exist. **There is no HTTP entry point for any of it** — no controller, route, request or view.
The config tables can only be populated with SQL, which makes the feature unreachable by the people
who run a school.

## (a) Discovered stack, and the pattern each screen follows

### Stack

| Layer | What it is |
| --- | --- |
| Server | Laravel, **Inertia** (`@inertiajs/react`), `HandleInertiaRequests::share()` |
| Client | **React 19 + TypeScript**, Radix primitives under `resources/js/components/ui/` (shadcn-style), Tailwind v4 |
| Routing helper | **Wayfinder** (`@laravel/vite-plugin-wayfinder`) — generated, gitignored, regenerated by `bin/quality` |
| In-page data | **axios** against `/api/*` for tab-style screens; Inertia props for page-level screens |
| Feedback | `react-toastify` (`toast.success` / `toast.error`) |
| Design rules | [`docs/ui-ux-design-system.md`](../ui-ux-design-system.md) — canonical reference implementations listed at its top |

**Not Vue, not Livewire, not Blade.** Determined from `package.json`, `resources/js/app.tsx`
(`createInertiaApp`), and the `.tsx` page tree.

### The two established page patterns

**Pattern A — Inertia page.** Controller returns `Inertia::render('admin/…', [...props])`; the page
reads `usePage().props`. Used for list/detail screens (`pages/admin/students/index.tsx`).

**Pattern B — setup tab.** A React component rendered inside `pages/admin/setup.tsx`'s tab switch,
fetching and mutating through `/api/*` with axios, using `Modal` / `Confirm` / `Empty` from
`components/setup/setup-ui.tsx` and toasts for feedback. This is how every academic-configuration
screen is built today (`components/setup/class-structure-tab.tsx`, `pages/admin/exam-types-tab.tsx`,
`grading-schemes-tab.tsx`, …).

**All progression *config* screens follow Pattern B**, because they are academic configuration and
belong beside class structure. The reassignment action and any rollover surface follow **Pattern A**
(they are operations on a page, not configuration tabs).

### Routing conventions

- Config/CRUD endpoints live in **`routes/api.php`**, grouped by permission middleware:
  - `permission:academic_setup.manage` — lines 47–203, contains `/class-structure/*`
  - `permission:admin_area.access` — lines 204–227, contains `move-from-ccm`, `backfill-term`, `curricula/queued`
  - `permission:academic_data.view` — lines 241–257, reference reads
- Inertia page routes live in **`routes/web.php`** (`setup/…`).
- Route-model binding is **by uuid**: `{classLevel:uuid}`.
- **Ordering matters**: a literal segment must be registered before a `{model:uuid}` wildcard.
  (`/curricula/queued` was a live 404 for exactly this reason — #277.)

### RBAC

- `App\Enums\Permission` is the catalogue. `academic_setup.manage` gates class structure;
  `admin_area.access` gates admin operations.
- **Every case must be filed in `App\Enums\PermissionGroup`** — `Permission::group()` resolves with
  no fallback and `PermissionGroupTest` asserts the groups partition the enum exactly. An unfiled
  case fails the suite by design.
- Frontend gating is **`<Can permission="…">`** / `usePermissions()`, fed by `auth.permissions`
  (`EffectivePermissions::for($user)`) shared in `HandleInertiaRequests`. It reflects the real Gate,
  including the super-admin bypass — so a control never shows for something the server would deny.
- Adding a **new** permission means: enum case → `PermissionGroup` filing → `RbacSeeder::grantsMap()`
  → run `php bin/ci-grants-convergence-lint.php` and ship a convergence migration if it demands one.

### School scoping

School-owned models use `BelongsToSchool` (global `SchoolScope`). The established controller idiom
resolves a submitted uuid **through the school relation**:

```php
$school = ActiveSchool::getOrFail();
$gradingSchemeId = $request->grading_scheme_id
    ? $school->gradingSchemes()->where('uuid', $request->grading_scheme_id)->value('id')
    : null;
```

That single line is what keeps a cross-school id out. **Every picker in this plan resolves the same
way**, and every list endpoint returns same-school rows only because the scope applies.

### ⚠️ Validation errors do not currently surface — do not copy this

`ClassLevelArmController` wraps each action in `try { $request->validate(...); … } catch (\Throwable
$th) { return response()->json(['error' => 'Failed to create level'], 500); }`.

`ValidationException` **is** a `Throwable`, so it is caught: a validation failure returns **500 with
a generic string**, not 422 with field errors. The frontend matches it — `toast.error('Failed to
save level')`. Field-level messages cannot reach the user through this path at all.

**This plan uses `FormRequest` classes instead**, which validate *before* the controller body runs,
so failures render as 422 with `errors` and never enter the try/catch. The frontend reads
`error.response.data.errors` and renders per-field messages. This is the one place the plan
deliberately **does not** extend the nearest existing pattern, and the reason is that the whole
point of these screens is to tell an operator what is wrong *before* the rollover.

### B1 · Progression config, per class level

**Extends** the existing class-structure surface. Three of the five fields are scalar columns on
`class_levels`; two are set-valued and need their own editors.

| Field | Storage | Control |
| --- | --- | --- |
| `next_class_level_id` | column | same-school class-level picker, nullable ("terminal / graduating year") |
| `default_exam_type_id` | column | same-school exam-type picker, nullable |
| `arm_distribution_strategy` | column | radio / select, exactly `round_robin` \| `explicit_only` |
| Term participation | `class_level_term_participation` | add/remove rows of `(term_order, is_ccm)` — **presence is participation** |
| Exam-type set | `class_level_exam_types` | multi-select of same-school exam types |

**Routes** (in the `academic_setup.manage` group, `routes/api.php`):

```
GET    /api/class-levels/{classLevel:uuid}/progression      → show
PUT    /api/class-levels/{classLevel:uuid}/progression      → update (the three columns)
POST   /api/class-levels/{classLevel:uuid}/participation    → add (slot, is_ccm)
PATCH  /api/class-levels/{classLevel:uuid}/participation/{participation:uuid} → toggle is_ccm
DELETE /api/class-levels/{classLevel:uuid}/participation/{participation:uuid} → remove
PUT    /api/class-levels/{classLevel:uuid}/exam-types       → sync the set
```

**Controller:** new `ClassLevelProgressionController`. Not added to `ClassLevelArmController` — that
class is already 300+ lines across four entities.

**Form requests and the DB-mirroring rules** (each mirrors a constraint the database or a job
already enforces, so the operator is told *before* the write):

`UpdateClassLevelProgressionRequest`
- `next_class_level_id` — `nullable|uuid|exists:class_levels,uuid`, resolved through the school
  relation. **Mirrors:** the composite FK `(next_class_level_id, school_id)`.
- **not self** — `next_class_level_id` must not be this level's uuid. **Mirrors:**
  `class_levels_progression_guard_bi/_bu` (the trigger from `2026_08_20_130000`).
- **no cycle** — reject if setting this pointer would create a ring. **Mirrors nothing in the DB**:
  the trigger catches `A→A` only; `A→B→A` is legal at every row. This is the check
  `academics:validate-progression` performs, and the UI must perform the same walk *before* saving,
  because the rollover command will otherwise refuse the whole run at the worst moment.

  **EXTRACT THE WALK INTO ONE SHARED CHECKER** (e.g. `ProgressionGraph::findCycle()`), called by both
  this FormRequest and `ValidateProgressionGraph`. Two implementations of the same graph walk will
  drift, and the command is the one that has tests today. Same reasoning the plan applies to
  `RolloverPlanner` in B4. Do this as part of M1, not later — the command's iterative walk moves into
  the service and the command becomes a thin caller.
- `default_exam_type_id` — `nullable|uuid|exists:exam_types,uuid`, school-resolved.
- `arm_distribution_strategy` — `required|in:round_robin,explicit_only`. **Mirrors:** the trigger's
  value guard.

`StoreParticipationRequest`
- `term_order` — `required|integer|min:1`.
- **unique (class_level_id, term_order)** — **mirrors:** `class_level_term_participation_unique`.
- `is_ccm` — `boolean`.

`SyncClassLevelExamTypesRequest`
- `exam_type_ids` — `array`, each `uuid|exists:exam_types,uuid`, school-resolved. **Mirrors:**
  `class_level_exam_types_unique` and the composite FK.
- **resolvability check** — warn (not block) when the set is empty *and* `default_exam_type_id` is
  null, because `MoveToNextYearJob::resolveExamType` hard-stops in that case and silently leaves
  every pupil of that level unplaced.

**Response shape:** `ClassLevelProgressionResource` — the three columns as uuids (never ids),
`participation: [{uuid, term_order, is_ccm}]`, `exam_types: [{uuid, name}]`, plus a computed
`is_terminal` so the UI does not re-derive it.

**Frontend:** new `components/setup/progression-tab.tsx` registered in `pages/admin/setup.tsx`'s tab
switch, or a "Progression" section inside the existing class-structure tab (open question 3). Uses
`Modal`, `Confirm`, `Empty`, `<Can permission="academic_setup.manage">` on every mutating control.

**Edge cases:** terminal level (null next) must be explicit and visible, not an empty select;
removing a participation row that is a level's only slot must warn (the end-of-year selection uses
`MAX(term_order)` and finds nothing); changing `arm_distribution_strategy` to `explicit_only` should
warn if no arm map exists for that level's arms, because every unmapped pupil will be left unplaced.

**Tests:** feature tests per endpoint (happy path, each DB-mirroring rule rejected with 422 and the
right field key, school isolation — another school's level uuid is a 404/422, never an update).
Frontend: a component test that the cycle check blocks save and names the ring.

### B2 · Arm progression map

`class_level_arm_progressions`: `source_class_level_arm_id` → `target_class_level_arm_id`, UNIQUE on
source.

**Routes** (`academic_setup.manage`):

```
GET    /api/class-levels/{classLevel:uuid}/arm-map     → list for this level's arms
PUT    /api/class-levels/{classLevel:uuid}/arm-map     → sync
DELETE /api/arm-progressions/{progression:uuid}        → remove one
```

**The rule the database does not enforce.** `MoveToNextYearJob::resolveArm` **refuses** a mapped
target whose `class_level_id` is not the source level's `next_class_level_id` — it does not fall
through to label matching, it leaves the pupil unresolved. No FK expresses this. So
`SyncArmProgressionRequest` must validate:

- source arm belongs to this class level;
- **target arm's `class_level_id` === this level's `next_class_level_id`** — the load-bearing rule;
- both arms are same-school (school-resolved uuids);
- one target per source (**mirrors** `class_level_arm_progressions_source_unique`).

**Frontend:** a two-column mapper — source arms down the left, a target picker on the right whose
options are **only** the arms of `next_class_level_id`. Constraining the options is the primary fix;
the server rule is the backstop. If the level has no `next_class_level_id`, the whole editor is
disabled with an explanation rather than showing an empty picker.

**Edge cases:** changing `next_class_level_id` while a map exists **invalidates every row** — the UI
must detect this on save and offer to clear the map, because leaving it silently strands the cohort
at rollover. Arms that exist in the source level but not the target (the real Y11 `H` → Y12 case)
should be shown as "will distribute" rather than as an error.

**Tests:** the wrong-level target is rejected with a message naming both levels; the picker lists
only target-level arms; changing `next_class_level_id` surfaces the invalidation.

### B3 · Reassignment action

`CurriculumReassignmentService::reassign(StudentCurriculum $current, Curriculum $newCurriculum, User
$performedBy, ?string $reason = null): StudentCurriculum`.

**Route** (`admin_area.access`, or `student_curriculum.promote` — open question 2):

```
POST /api/student-curricula/{studentCurriculum:uuid}/reassign
```

**Controller:** `StudentCurriculumController::reassign` — the service is already transactional, so
the action resolves the target curriculum through the school, calls `reassign`, and returns both
episodes.

**Request:** `ReassignStudentCurriculumRequest` — `curriculum_id` required uuid, school-resolved;
optional `reason` string. **The cross-school case is already refused by the service** with
`BusinessRuleException`; the request's school resolution means it should never get that far, and the
controller catches it as a 422 rather than letting it 500.

**Response:** `{ from: StudentCurriculumResource, to: StudentCurriculumResource }` so the UI can show
"old episode → transferred, new episode → active" without a refetch.

**Frontend:** a modal on the student detail page and on the class list row, target picker listing
same-school curricula (default: other arms of the same class level, since arm correction is the
common case). Gated with `<Can>`.

#### ⚠️ `transferred` collides with an existing enum value — resolve the LABEL before building

`students.status` is `enum('active','withdrawn','graduated','transferred')`. **`transferred` already
existed on the membership enum** (`StudentMembershipStatus::TRANSFERRED`) and means *the pupil left
this school*. `student_curricula.status` now also has `transferred`, meaning *this episode was
vacated by a reassignment*. Two tables, the same word, materially different meanings — a pupil could
show "Transferred" (gone) beside an episode showing "Transferred" (moved arm).

This was introduced with the reassignment service and not noticed until this sweep. Renaming the
stored value is expensive now (merged, pending deploy), and the value is right in isolation. **Fix it
at the display layer.**

**SETTLED: the episode word is "Reassigned", end to end.** Every `transferred` episode is the output
of the reassignment service and nothing else, so the label matches the verb the operator clicked —
button **"Reassign"**, badge **"Reassigned"**, filter option **"Reassigned"**, audit line
**"Reassigned from 8B to 8S"**. One verb from click to record. "Moved" is friendlier but severs that
thread and reads vaguer in an audit line. Membership status keeps **"Transferred"** (the pupil left
the school).

Decided at plan time rather than at B3 build time precisely because the word lands in a badge, a
filter and an audit line simultaneously, and three different words is what happens otherwise.

#### The actual `transferred` surface — swept, not assumed

The sweep found the frontend blast radius is **much narrower than the plan first claimed**, and one
row of the original table was simply wrong.

| Reader | Verdict |
| --- | --- |
| `components/student-curricula-page.tsx:12` (`StudentCurriculumStatus` union) | **change** |
| `components/student-curricula-page.tsx:16-21` (`STATUS_OPTIONS`) | **change** — filter list only |
| `components/student-curricula-page.tsx:23-28` (`STATUS_BADGE`) | **change** — and note it is `Record<StudentCurriculumStatus, string>`, an exhaustive mapped type, so **tsc fails until it is updated**. The compiler is the guard here; the tsc ratchet in `bin/quality` will catch an omission. |
| ~~`pages/admin/students/index.tsx:511,523`~~ | **NOT AFFECTED — the original plan was wrong.** That reads `student.status`, which is `StudentMembershipStatus` (active/withdrawn/graduated/transferred), a different enum on a different table. |
| `app/Academics/BillableEnrollmentAdapter.php:257-271` | **No change needed, and the reason matters.** It selects billable episodes with an **allowlist** (`status = ACTIVE`), not a denylist — so a vacated `transferred` episode drops out of billing automatically and the destination (active) episode bills. Had it been written as "not withdrawn", a transferred episode would have kept billing silently. Worth a regression test pinning the allowlist, since that is what makes it safe. |
| `app/Concerns/ResolvesTermFilter.php:50-62` | **Decide.** Past-term views list `active|promoted|repeated`. A vacated episode is historical — including it would double-list a pupil across the old and new arm for that term. Recommendation: leave it out, and say so in the code. |
| `UpdateStudentCurriculumStatusRequest` | **No change.** `Rule::in(['active','repeated','withdrawn'])` — `transferred` stays unsettable by an admin, exactly as `promoted` is. It is a state a pupil *arrives at*. |

No `match`/`switch` on an enrollment status exists in PHP, and the other frontend `switch (status)`
sites (`sessions-tab`, `bulk-update`, `students/show`, `guardians/import`) switch on term, import or
membership statuses — none on `StudentCurriculumStatus`.

**`transferred` is filterable but not settable.** `UpdateStudentCurriculumStatusRequest` allows
`active|repeated|withdrawn` only, and `transferred` must stay out of it for the same reason
`promoted` is out: it is a state a pupil *arrives at* via the service, never one an admin asserts.
The status dropdown and the filter list are therefore **different lists** — worth stating in the
code, because they are the same list today.

**Edge cases (all already handled by the service; the UI must render them as outcomes, not errors):**
already in target → no-op, show "no change"; already ended → no-op; move back a level → the
promotion is **undone** and the link cleared; revive → the pupil's earlier subjects *and any scores
from that stint* come back, which the modal should say plainly before confirming.

**Tests:** feature test per path (happy, no-op, cross-school 422); a test that the status dropdown
does not offer `transferred` while the filter does.

### B4 · Rollover operator surface

**Decide first (open question 1): CLI-only, or UI.** Both are defensible and the plan below is what
the UI costs if chosen.

The commands are `academics:run-end-of-term {term}` and `academics:run-end-of-year {sourceSession}
{targetSession}`, both `--user=` + `--commit`, dry-run by default, dispatching a `Bus::batch`.

**Routes** (proposed `academics.rollover`):

```
POST /api/rollover/end-of-term/preview     → the plan, no dispatch
POST /api/rollover/end-of-term             → --commit equivalent
POST /api/rollover/end-of-year/preview
POST /api/rollover/end-of-year
GET  /api/rollover/batches                 → progress
```

**Controller:** `RolloverController`. It must **not** shell out to artisan. The selection logic and
the two gates should be extracted from the commands into a shared service
(`RolloverPlanner`) that both the commands and the controller call — otherwise the UI and the CLI
drift, and the CLI is the one with the tests.

**The surface must say "queued", not "done".** `--commit` dispatches a batch and returns; the
migration happens as workers drain the queue. A progress view reads `job_batches`
(`total_jobs`, `pending_jobs`, `failed_jobs`, `finished_at`, `cancelled_at`; batch names are
`rollover:{kind}:school:{id}:…`) and shows **queued N / done X / failed Y**, with an explicit
"the rollover is not finished until this batch drains — do not change the current session yet".

**Both gates must render as on-screen errors, not exit codes:**
- **cycle** — `academics:validate-progression` output, naming the ring, with a link to B1 to fix it;
- **CCM still active** — the list of offending curricula, with a link to the CCM move screen.

**Edge cases:** re-running while a batch drains is safe but wasteful (the commands warn; the UI
should too); a partially failed batch needs re-queuing, so the commit action must stay available.

**Tests:** feature tests asserting *nothing is dispatched* on either gate (`Bus::fake()` +
`assertNothingBatched`), preview/commit parity, and that the batch view reports the counts it reads.

## (c) Sequencing

### M0 · `academics:seed-progression-defaults {school}` — the missing prerequisite

**The screens edit config; nothing populates it.** On the day they ship, both live schools have empty
`class_level_term_participation`, empty progression pointers, empty exam-type sets and no arm maps —
so every job no-ops and nothing rolls over until a human hand-enters all of it. Across ~6–10 levels
per school that is a large, error-prone pass, and `next_class_level_id` is precisely where one wrong
link silently strands a cohort at rollover.

A **dry-run seed command** that infers a reviewable draft from structure that already exists:

- **participation** ← the term orders each level's existing curricula actually use;
- **`next_class_level_id`** ← `order + 1` where a next level unambiguously exists;
- **exam-type set** ← the exam types that level's current curricula carry;
- **`default_exam_type_id`** ← the most common of those, where unambiguous;
- **`arm_distribution_strategy`** ← `round_robin`.

Dry-run by default, `--commit` to write, mirroring `academics:backfill-promotion-links`. It is a
**draft the operator ratifies through the B1/B2 screens**, not an authority — which is why `order + 1`
is acceptable here even though the runtime rejects that inference (the plan's own reasoning for the
explicit pointer). It turns day one from blank-slate data entry into review-and-adjust.

It must refuse to overwrite existing config (or require `--force`), so re-running after hand-editing
cannot silently revert someone's corrections.

### Milestones

| Milestone | Contents | Why here |
| --- | --- | --- |
| **M0 — Seed command** | `academics:seed-progression-defaults`, dry-run first | **Beneath M1.** Without it the config screens open onto nothing and every school pays a manual pass. |
| **M1 — Progression config (B1)** | columns + participation + exam-type set, with the shared cycle checker | **Hard prerequisite.** Until these tables can be populated by a human the feature is unreachable, and both jobs no-op without participation rows. |
| **M2 — Arm map (B2)** | the mapper + the target-level rule | Depends on `next_class_level_id` existing (M1). Without it, end-of-year distributes everything. |
| **M3 — Reassignment (B3)** | action, modal, `transferred` everywhere | Independent of M1/M2 and useful on its own — it is also the correction tool for a rollover that placed someone wrong, so it should land **before** any rollover runs. |
| **M4 — Rollover surface (B4)** | preview, commit, batch progress | Last, and only if the answer to open question 1 is "UI". Needs M1 and M2 to be meaningful. |

M3 could run in parallel with M1/M2 — it touches a different controller and different pages.

## (d) Decisions — all five settled in review

**1 — Rollover stays CLI-only for v1. M4 is deferred, with a named trigger.**

Dry-run default, once-a-term, shell access is the gate. But this is **operational debt with an end
condition, not a permanent answer**. Build M4 when either becomes true:

- there are more schools than a developer is willing to babysit through a rollover; or
- a registrar is expected to run one themselves.

**The two gates are NOT symmetric, and the plan previously blurred them:**

| Gate | Nature | What config time can do |
| --- | --- | --- |
| **Cycle** | pure config property | **Fully verifiable.** Walk the graph when `next_class_level_id` is edited and refuse the save. Do this. |
| **CCM in a final slot** | **runtime state** — depends on where pupils are at rollover | **Only nudgeable.** B1 can say "this level runs CCM in its final slot — the CCM move must run before the rollover", but it cannot verify it. The real gate stays the command's abort, which the CLI operator sees. |

Do not let any screen imply config time covers CCM. It covers the cycle and *nudges* on CCM.

**2 — Permissions: no new one now.**
- Config (B1, B2): **`academic_setup.manage`** — existing, exactly the right scope.
- Reassignment (B3): **`student_curriculum.promote`** — same class of act. Split it out only if
  cross-level demotion later needs tighter control than an arm nudge.
- Rollover: **do not add `academics.rollover`.** With CLI-only, the gate is shell access and the enum
  case buys nothing — pure cost (enum + `PermissionGroup` filing + `grantsMap()` + possibly a
  convergence migration) for a control no screen checks. Add it *with* M4. **No permission exists
  until something checks it.**

**3 — A panel per class level, inside class-structure. Not a thirteenth tab.**
Progression config is a property of a *specific* level — you configure it *for* Year 11, not in the
abstract. A standalone tab would need its own level picker, duplicating the selection
class-structure already has. A "Configure progression" affordance on each level row opens a
Modal/panel reusing the existing list. `ClassLevelProgressionController` stays separate regardless.

**4 — FormRequest + 422 + per-field rendering. Endorsed, and the neighbour is a bug.**
The setup-tab pattern swallowing `ValidationException` into a generic 500 is not a pattern to match —
it is a latent defect that makes field errors invisible on those screens too. The divergence is
correct, not regrettable. **File a tech-debt ticket** to migrate the old tabs' error handling; do not
do it in this work.

**5 — `is_ccm` participation: defer editing.**
Create participation rows `is_ccm = false`. Keep the PATCH endpoint in the API (cheap), leave the
toggle out of the UI until a school needs CCM slots.

## (e) Remaining notes to fold in at build time

**N1 — The reassignment target picker must not be a flat list.** Every same-school curriculum is
hundreds of rows. Use a level → arm cascade, or a search, defaulting to the other arms of the
pupil's current class level (arm correction is the common case).

**N2 — Editing progression config while a rollover batch is draining** lets in-flight jobs read
shifting config. Low probability (both happening at once is rare), but currently undefined. Add a
warning — or a soft guard — on the B1/B2 screens when an unfinished `job_batches` row exists for the
school, reusing the same query the commands' `warnIfBatchStillDraining` already runs.

**N3 — Pin the billing allowlist with a test.** `BillableEnrollmentAdapter` is safe for `transferred`
only because it selects on `status = ACTIVE` rather than excluding terminal statuses. That is a
property worth a regression test, since the safe version and the unsafe version look equally
reasonable to a future editor.
